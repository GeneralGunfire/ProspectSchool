# Prospect Mobile (Android)

The Android app is the existing web app wrapped in [Capacitor](https://capacitorjs.com) —
Capacitor loads the same Vite build (`dist/`) into a native WebView, so
nothing in `src/` changes to support it beyond the shared native-app
detection in `src/lib/nativeApp.ts` (also used by the Tauri desktop app —
see `DESKTOP.md`). Styling, layout, and behavior are identical to the web
app; see `android/` (the native Android Studio project) and
`capacitor.config.ts` for the wrapper config.

**Scope: Android only, sideloaded APK.** No iOS, no Google Play Store
distribution — same "direct download from our own site" model as desktop.

## Prerequisites

- Node (already required for the web app)
- Java 17 (Temurin recommended) — https://adoptium.net
- Android Studio (for local builds/emulator) — https://developer.android.com/studio, or just the command-line tools + `ANDROID_HOME` set if you don't need the IDE

## Local development

```bash
npm install
npm run android:sync   # builds the web app and copies it into android/
npm run android:open   # opens the project in Android Studio
```

Run the app from Android Studio onto an emulator or a connected device.
There's no Capacitor equivalent of `desktop:dev`'s live-reload window —
after any `src/` change, re-run `npm run android:sync` and re-run from
Android Studio (or use Capacitor's `npx cap run android --livereload` for
a live-reload dev loop pointed at the Vite dev server, if useful).

## Local build

```bash
npm run android:build
```

Produces a debug APK at `android/app/build/outputs/apk/debug/*.apk`.

## CI build

`.github/workflows/mobile-android.yml` builds the Android APK on:
- pushing a tag matching `android-v*` (e.g. `android-v0.1.0`)
- manual trigger (Actions tab → "Mobile (Android)" → Run workflow — note: this does NOT publish a Release, since there's no tag to attach one to; use a tag push for a real distributable build)

**Required repo secrets** — same 5 secrets as the desktop workflow (see
`DESKTOP.md`): `VITE_SITE_URL`, `VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY`,
`VITE_SUPABASE_SERVICE_ROLE_KEY`, `VITE_GROQ_API_KEY`. The workflow includes
the same fail-fast "Verify required secrets are set" step the desktop
workflow needed adding after 3 builds silently shipped with blank
credentials — this one has it from the start.

On a tag push, the built APK is both uploaded as a workflow artifact
(`prospect-android-apk` — requires a signed-in GitHub session, not
user-facing) **and** attached to a published GitHub Release matching the
tag (publicly downloadable, no login required).

### Cutting a new release

```bash
git tag android-v0.1.0
git push origin android-v0.1.0
```

## App icon

`resources/icon-foreground.png`, `resources/icon-background.png`, and
`resources/icon.png` are generated by `node scripts/android-icon-assets.mjs`
from `public/logo-dark-mode.png` — same dark-plate treatment as the desktop
app icon (`src-tauri/icons/`). Re-run that script if the source logo
changes, then regenerate every density bucket with:

```bash
npx capacitor-assets generate --android
```

## External links (past papers, resources, attachments)

Shared with desktop — see `src/lib/openExternal.ts`. On Android,
`Capacitor.isNativePlatform()` routes external URLs through
`@capacitor/browser`'s `Browser.open()` instead of `window.open()`, which
doesn't reliably open a real browser from inside a WebView.

## Known items still open

- **This build is unsigned** in the sense that it's a debug APK, not a Play-Store-style signed release build — Android will show an "install from unknown sources" prompt (expected, same posture as desktop's unsigned SmartScreen warning). A signed release build (with a real keystore) is a future step if this ever needs to feel more "official," not required for sideloading to work.
- Geolocation (`navigator.geolocation`, used in location-input flows) hasn't been verified inside Capacitor's WebView yet — may need the `@capacitor/geolocation` plugin plus `ACCESS_COARSE_LOCATION`/`ACCESS_FINE_LOCATION` added to `android/app/src/main/AndroidManifest.xml` if permission prompts don't fire correctly with the raw browser API alone. Flagged, not yet fixed.
- Auto-updates are not wired up (no in-app update-check mechanism) — same status as desktop.
- Not yet tested on a real device or emulator — this is an unverified scaffold, same caveat the desktop scaffold had before its first real build.
